## Security Notes

- JWT is stored only in a `SameSite=Strict` cookie (`userAuthToken`), never in `localStorage`/`sessionStorage`, never logged to console, never placed in a URL/query param — verified by test and by reading every new file.
- No `Secure` attribute on the cookie — **this exactly mirrors the pre-existing pattern in `src/app/utils/auth.tsx`'s `adminToken` cookie**, so it's not a regression introduced by this module, but is worth noting since it was copied forward rather than improved.
- **Known issue (copied from the pre-existing pattern, not new)**: `getUserToken()` reads the cookie via `match.split("=")[1]`, which only returns the substring up to the *second* `=` in the cookie row. If a token's own base64 segment legitimately contains `=` padding, the value is silently truncated on read (proven with an explicit test in `userAuth.test.ts`: a token ending in `signature==` is read back as `signature` only). This is byte-for-byte the same pattern already present in `src/app/utils/auth.tsx`'s `getToken()`, so it predates this module and isn't a new defect — but the module reproduces it verbatim rather than fixing it. Recommend `match.split("=").slice(1).join("=")` or `decodeURIComponent(match.slice(match.indexOf("=") + 1))` in both places if this is ever revisited (out of scope for this QA pass since it mirrors an accepted existing pattern).
- `admin-panel` route correctly redirects non-`admin` roles to `/user-auth/dashboard` client-side via `useUserAuthGuard("admin")` — confirmed by test. Per the repo's own documented pattern for `useAuthGuard`, **this is client-side defense-in-depth only** and is not a substitute for backend authorization; the report does not treat it as one.
- No hard-coded credentials, API keys, or secrets found in any new file (manual grep + read of every file).
- Signin form label reads "Username or Email" but the backend contract (and every other call site in this repo) is username-only — a minor UX/copy mismatch, not a security issue, flagged for the implementer's attention.
